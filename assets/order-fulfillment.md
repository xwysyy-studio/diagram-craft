# 订单履约：支付、超时与异步补偿

这是用于检验技术示意图表达能力的虚构方案，不代表某个公司的真实实现，也不声称吞吐量、延迟或端到端严格一次执行。

## 下单与库存预留

客户端携带幂等键提交订单。订单服务先查该键是否已有订单：已有则返回原订单，不重复创建；没有则创建待支付订单，并向库存服务申请预留库存。

幂等键的登记与新订单创建在同一事务中完成，唯一键冲突时复用已有订单。

库存不足时，订单关闭并返回库存不足。预留成功后，订单服务创建支付单，登记超时任务，并向客户端返回订单号与支付入口。超时任务只在库存预留成功的订单上登记。

## 支付与超时的竞争

支付平台发送成功回调。回调接收器先验证回调合法性并按支付事件 ID 去重；不合法的回调拒绝处理，已经处理过的事件直接确认，不重复推进订单。

合法的新事件由订单服务读取当前订单状态：

- 待支付：尝试把状态从“待支付”条件更新为“已支付”。成功时，在同一数据库事务中写入订单已支付事件的 Outbox 记录。
- 已关闭：订单不重新打开，创建退款请求，进入退款处理。
- 已支付或已进入履约：确认回调，不重复产生履约事件。

超时处理器到时尝试把状态从“待支付”条件更新为“已关闭”。成功时，通知库存服务释放预留；如果订单已支付或已关闭，则不再执行关闭或释放动作。

支付与超时都以同一订单的“待支付”状态作为条件更新前提。竞争失败的一方重新读取状态，按上述对应分支处理；不得把失败的支付更新直接当作支付成功，也不得在订单已经支付后释放其预留。

## 异步履约与恢复

Outbox 发布器将订单已支付事件投递到消息队列，发送失败时保留未发布记录并重试。消息可能重复投递。

履约消费者按订单号检查处理记录，已经成功处理过的事件直接确认。新事件先把库存预留转为正式扣减，再创建发货任务。两个动作使用同一个订单号作为幂等依据；如果库存已经扣减而发货任务创建失败，重试只继续未完成的动作，不重复扣库存。

履约成功时，将订单更新为已完成并通知客户端。可重试失败进入待重试队列后返回履约消费者；达到处理策略的重试边界，或遇到不可重试失败时，转入人工处理，不标记为已完成。这里不指定重试次数或时间间隔。

退款成功后记录已退款并通知客户端；退款失败时转入人工处理，订单仍保持关闭，不转入履约。
